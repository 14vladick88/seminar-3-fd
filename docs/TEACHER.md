# План семинара для преподавателя

10-й класс, третье занятие. Основная часть — 01–03, задачи 04–05 для успевающих.
Предполагается, что ученики уже прослушали лекцию об ООП. Не объясняйте весь SOLID в эти же 90 минут.

| Минуты | Действие |
|---|---|
| 0–15 | Fork, включение Actions, clone, импорт Gradle. Покажите ожидаемую ошибку TODO, затем путь к логу. |
| 15–30 | Разминка 01 и 02. Если 02 затягивается, оставьте функцию поиска на дом и переходите к ООП. |
| 30–40 | Краткий разбор класса, объекта и управления состоянием. |
| 40–65 | Проездной: проверки до изменения, private set, независимость экземпляров. |
| 65–80 | Завершение основной части; успевающим — 04, затем 05. |
| 80–85 | Финальный commit и push, проверка актуального запуска Actions. |
| 85–90 | Финальный push, ссылки на форк и запуск, короткий разбор. |

Перед занятием откройте проект на чистой машине / профиле с JDK 17 и прогрейте зависимости.
Попросите учеников клонировать проект и завершить Gradle sync до пары, если есть такая возможность.
Проверьте доступность GitHub и загрузок Maven/Gradle в аудитории. Покажите различие между форком и исходным репозиторием.

## Что считать выполнением

- Базовый результат для отстающих: 01 и 03, умение прочитать причину падения теста.
- Основная часть: все тесты 01–03 зелёные.
- Расширенная часть: 04 зелёная и ученик объясняет полиморфный вызов.
- Дополнительная часть: 05 зелёная и ученик объясняет, зачем передавать интерфейс в конструктор.

Красный общий workflow из-за нерешённой дополнительной задачи не означает провал основной части.
Тесты — обратная связь, не защищённая экзаменационная система: ученик владеет форком и может изменить проверки.
При оценивании смотрите изменения тестов/workflow и попросите объяснить решение. Не требуйте PR и не объединяйте студенческие решения в шаблон.

## Вопросы для обсуждения

- Чем чётность N отличается от чётности суммы цифр его двоичной записи?
- По какой записи вычисляется второй добавляемый бит?
- Почему в задаче возвращаем N, а не R? Как проверить строгость неравенства?
- Что произойдёт со второй картой, если потратить поездку на первой?
- Почему нельзя предоставить публичный setter остатка?
- Как label узнаёт стоимость неизвестного ему вида доставки?
- Как протестировать уведомление без настоящей отправки?

## Техническое устройство

Пять независимых Gradle-модулей, Kotlin/JVM, JDK 17, kotlin.test + JUnit Platform.
CI запускается на push любой ветки и вручную; пять matrix jobs с `fail-fast: false`.
В job запускается только выбранный модуль. Ошибки не маскируются через continue-on-error.
Сводка формируется из XML; HTML и XML сохраняются как artifacts даже при падении тестов.
На занятии ученики проверяют решения через commit → push → Actions. Локальный запуск тестов пока не объясняем; преподаватель может использовать Gradle Wrapper для подготовки. Внешние сервисы и секреты ученикам не нужны.

Task05 содержит собственный готовый TravelCard, чтобы не зависеть от реализации task03.
Заготовки уже задают структуру классов: на первом занятии ученики дописывают поведение.
Для сильных учеников после основных тестов можно предложить самостоятельно добавить ещё одного потомка Delivery.
